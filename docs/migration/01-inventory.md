# Step 1-A. 현행 스키마 인벤토리 (실측)

작성 2026-09-05. 추측이 아니라 **실제 시트 데이터를 읽어서** 작성했다.
마이그레이션의 첫 번째 조건은 "한 필드도 잃지 않는 것"이므로, 여기 적힌 이상 항목은
모두 목표 스키마에 대응하는 처리 규칙이 있어야 한다.

### 데이터 정리 과제 (마이그레이션 시 처리)

1. **제목 KO/EN 분리** — 전 행. `\n` 기준 분리. (관리자 화면은 2026-09-05에 이미 `title_en` 컬럼 저장으로 전환됨)
2. **캡션 KO/EN 분리** — `HD-2026-006`, `HD-2026-007`
3. **재료 KO/EN 분리** — `HD-2026-006`, `HD-2026-007`, `HD-2026-008`
4. **날짜 형식 통일** — `.` 구분과 `-` 구분 혼재. `HD-2026-006`, `HD-2026-007`이 `.` 형식
5. **`price = "Artist Archive"`** — 가격이 아니라 상태 설명. `list_price = NULL` + 내부 메모로 이관
6. **전시별 대체 캡션** — `note`에서 꺼내 `exhibition_works`의 캡션 오버라이드로 이관
7. **제목 오타** — `Limited Editon` → `Limited Edition` (012·013·014, 작가 확인 필요)
8. **에디션 3행** — `HD-2026-012/013/014`는 같은 작품의 에디션 3점(각 qty 3, sold_qty 1). 현재 발행 스크립트가 013·014를 **ID 하드코딩으로** 제외 중

## 2. 전시 / Press 시트

`exhibitions`: `id, title, venue, start_date, end_date, work_nos, docent_url, type, note_public`
- `type`: `개인전`(1) / `단체전`(6) / `아트페어`(7) — 한국어 리터럴, 프론트가 `r.type === '개인전'`로 직접 비교
- `docent_url`, `note_public`: 전 행 비어 있음 (미사용)
- `work_nos`: 쉼표 연결 문자열. `EX-2026-03`은 비공개 작품 `ER-2026-001`도 포함

`Press`: `no, outlet, date, title, url, quote, image, note`
- `note` = 기자명 바이라인(`김갑찬 기자` 등). 민감정보는 아니지만 **무토큰 공개 API가 `_row`와 함께 전부 반환** 중
- `image`는 외부 언론사 CDN 직링크 (핫링크 — 원본이 내리면 깨짐)

## 3. 전시 이력 이중 진실 — 실측 대조 결과

작품별 `출품 기간` 자유텍스트와 전시시트 `work_nos`를 날짜 기준으로 대조:

```
자유텍스트 42줄  vs  전시시트 46개 관계
불일치가 있는 작품 5건
```

**불일치 5건은 전부 동일 원인**: 아직 열리지 않은 개인전 `EX-2026-01`(2026-11-23, 나전칠기로 아트하는 法)이
전시시트에는 있고 작품 자유텍스트에는 아직 없음 — 정상이며 오류가 아니다.

**진짜 오류 1건**: `HD-2026-012`의 자유텍스트에 2026-07-30 전시가 두 이름으로 중복 기재
(`토이콘서울2026, 코엑스` / `어반브레이크 토이콘 서울, 코엑스` — 같은 전시).

> **결론: 전시시트가 자유텍스트의 상위집합이다.**
> `exhibition_works`를 단일 진실로 승격해도 이력이 소실되지 않는다. 마이그레이션 리스크 낮음.
> 다만 컷오버 전에 자유텍스트를 재대조해 위 중복 1건을 정리할 것.

## 4. 운영 의존성 (무엇이 아카이브를 읽고 쓰는가)

```
[쓰기]
관리자 패널 index.html ──POST──> Apps Script /exec ──> Google Sheet
                                        └──> Drive (이미지 업로드)

[읽기]
publish.py (GitHub Actions) ──GET ?action=list&token=──> /exec ──> Sheet
                            ──GET ?sheet=exhibitions|press──> /exec
                            ──> Drive 원본 다운로드 ──> WebP 3단 생성
                            ──> data/*.json 커밋 ──> GitHub Pages

[발행 트리거]
관리자 패널 "🚀 홈페이지에 반영" ──POST action=publish──> /exec
   ──repository_dispatch(GITHUB_PAT)──> publish.yml
매일 00:00 UTC cron + workflow_dispatch
```

**핵심**: 공식 홈페이지는 정적 `data/*.json`만 읽고 아카이브를 직접 호출하지 않는다
(2026-09-03에 제거 완료). 따라서 **아카이브를 통째로 바꿔도 홈페이지는 영향받지 않는다.**
이것이 이번 마이그레이션을 안전하게 만드는 가장 중요한 구조적 사실이다.

### 마이그레이션이 건드려야 하는 지점
| 대상 | 현재 | 이후 |
|---|---|---|
| `publish.py` 데이터 소스 | `/exec` GET | Supabase 조회 |
| 관리자 패널 fetch (~20곳) | `/exec` POST/GET | Supabase JS |
| 인증 | 공유 토큰(localStorage, URL) | Supabase Auth |
| 발행 트리거 | Apps Script + PAT | Edge Function + PAT(서버) |
| 이미지 | Drive `drive:FILEID` | **변경 없음 (Drive 유지)** |
| 홈페이지 | 정적 JSON | **변경 없음** |

## 6. 작가 결정 (2026-09-05, 확정)

1. **`Limited Editon` → `Limited Edition` 오타 수정한다.**
   오타는 *한글 제목* 필드에 있다(`조개배달부 얼빵해달 2026 Limited Editon`), 영문 필드가 아니다.
   `HD-2026-012`는 현재 공개 발행 중이라 **홈페이지에 그대로 노출되고 있으므로** 마이그레이션을 기다리지 않고 먼저 고친다.
2. **`HD-2026-012/013/014`는 1작품 3에디션으로 본다.**
   → `editions` 테이블 도입(02-target-schema.sql). 판매·소장 정보가 works에서 editions로 이동한다.
   유일작도 예외 없이 1/1 에디션 행을 갖게 해서 코드 경로를 하나로 유지한다.
3. **Press 이미지는 자체 사본을 보관한다.**
   `image_source_url`(출처 기록) + `image_file`(자체 사본) 분리.
   ※ 검토 필요: 언론사 사진의 재배포 권리. 다수는 작가가 제공한 작품 사진이라 문제없을 가능성이 높으나,
   언론사가 직접 촬영한 컷이 섞여 있으면 사본 보관과 재배포는 성격이 다르다. 작가님이 판단하실 영역.
4. **`ER-2026-001`(이벤트 리워드)은 공개하지 않는다.** → `kind='event_reward'`, `publish_web=false` 고정.
